# 设计与决策

2026-10-29：按用户要求沉淀 Mac mini 日活及周一三项周活的 CLI 使用知识，复用现有 `zzz-one-dragon-player`，不再创建同义日活技能。已有 Windows 内容保留，通过平台分支避免 Mac 会话误用 Windows 参数或从零安装。

- 用户明确要求正常任务只走 CLI；Computer Use 仅在真实阻断时用于诊断/修复。因此不把 GUI 路线当作自动任务备用流程。
- 现有 CLI 已具备当前账户整组、单项和无设备预览能力，直接记录它的真实参数；不新增平行任务框架或无必要脚本。
- 当日实测只证明预览、模型加载、启动和采集的部分能力。第一次在冷启动帧状态 3 停止，第二次在辅助功能/事件投递预检停止，未运行日活。把这个边界写进参考，防止未来把历史原机验收或能力提示误称成本机新验收。
- 资源范围来自本次用户授权：只用自然体力，不补电、不用储备道具或付费货币。不能把历史开发会话曾允许手动补电的权限带入定时任务。
- 当前部署没有主仓或测试仓的 `.git`，原配置的下载源指向上游。自动提交与推送目标必须另行明确；不擅自初始化仓库或推上游。
- 周活单项预览已通过，实机流程留到下一次获授权的周一验证。单项入口可能不同于整组跳过语义，所以保留独立的防重复验收项。
- 项目通用指南偏好只写方法论；本次用户明确要求记录已验证命令、环境与恢复步骤，因此放在技能内分场景参考文件，主入口只保留平台路由和关键判断。
- 更新原 frontmatter 时将旧 `version`、`author`、`tags` 移入 `metadata`，保留其值，同时符合当前 Codex 验证器支持的结构。
- 不安装到个人云技能、不上传或推送，不生成与本机 Codex 使用无关的 Windows junction。后续调度提示应明确读取项目内此 skill。

2026-10-30：继续实机测试后的补充决策。

- 原部署通过 NAS 双向同步，用户 MacBook 推送后核对4053个对应文件均与远端一致，但 `.git` 不同步。将“无法提交”改为已确认用户 fork 后从独立 Git 工作区修复，不对同步源 `git init`、覆盖或批量移动，避免把只在 mini 上的整理传播到另一台机器。
- 原 CLI 权限获得用户解决后，首帧及启动切屏仍有暂态，允许原期限内等有效帧，而非关掉输入保护。冷启动已实际到大世界，不能继续沿用“日活从未开始”的旧边界；历史失败单独保留。
- 卦象结果页存在可读文字先于可用确认按钮的动画，咖啡完整选项存在全半角差异。前者等按钮启用，后者规范化宽度后完整匹配；都没有把未知页面、模糊匹配或重复确认变成通行条件。
- 签到及咖啡通过原操作分段恢复，不能记成从头连续通过。体力中断发生在胜利已经记账之后，正是“只凭日志没尾就重跑”会重复消耗的场景，因此加入已记账结算恢复及跨04:00刷新防重判据。
- 继续诊断时设备已锁定。锁屏由用户手动解除，不能把用户先前授权辅助功能理解为自动解锁或扩大权限。当前只记录已完成三项、五卡3/3及单卡1/4；未完成部分和最终奖励缺证必须显式保留。

2026-10-30 08:10：用户解锁后实际完成新游戏日的400日活与可领奖励。保留前一日和07:00锁屏失败，新增最新结果而不覆盖历史。战斗沿用已有内圈模板并限定到单场，避免为接近阈值的一张图全局放宽保护；城募仅开放实读介绍页的一次Start，免费基础方案与付费解锁仍区分。城募等级奖励触发新的丁尼任务，实际再次用单项CLI领完，因此新增后续奖励复核方法。体力自然不足时原应用正常结束不等于计划全清；记录五卡1/3、单卡2/4和城募140/160，防止把400日活成功扩大为所有计划次数完成。


2026-10-31：用户明确要求在正式部署目录最小整合昨日已验收日活修复。当前两仓已有 Git 元数据，正式目录首帧等待及对应保护测试已有等效实现，保留它及用户迷失之地草稿，只补缺失的启动切屏、签到、对话、模拟室和城募差异及配套测试。旧技能中的原部署无 Git、必须独立运行等叙述改成历史边界，避免阻断已授权的正式目录修复；仍须每次核对实际源码，不能用同路径代替版本证明。保留当前 skip_plan、队伍、账户配置和体力计划；不因执行需求改写用户选择。
