# Mac OCR 原生内存增长修复

## 2026-10-30：更新 macOS ONNX Runtime 至 1.27.0

CLI 和原 GUI 均出现持续增长，最新 GUI 对照最大采样 footprint 为 10.537 GiB，不能归为 CLI 独有问题。此前 Operation 事件订阅泄漏已独立修复；本次处理另一个可在纯 CPU OCR 中复现的原生增长。

ORT 1.24.4 的 KleidiAI SME 卷积把输入内容哈希放入线程局部 LHS 缓存键，新内容即使尺寸不变也可能增加缓存项。有限截图反复回放会命中缓存，不能用第二轮稳定排除这个缺陷。上游 [问题 #28231](https://github.com/microsoft/onnxruntime/issues/28231) 和 [修复 #28363](https://github.com/microsoft/onnxruntime/pull/28363) 已明确该机制；[1.27.0 源码](https://github.com/microsoft/onnxruntime/blob/v1.27.0/onnxruntime/core/mlas/lib/kleidiai/convolve_kleidiai.cpp) 已移除输入内容键。本机 CPU 支持 SME/SME2，旧 Python 扩展包含相同线程局部缓存符号。

只将 Darwin 的 `onnxruntime` 固定至 1.27.0；Windows `onnxruntime-directml==1.24.4` 保持不变。锁文件只更新该包及项目对应依赖声明，不带入解析工具造成的其他包或格式变更。本机先隔离校验官方 wheel，兼容验证通过后使用 `uv pip install --no-deps` 替换单包；安装前后包清单仅 ORT 版本变化，未执行 `uv sync`。

没有降低实际 OCR 分辨率、改变模型、关闭 CoreML 或修改队伍、策略。也没有加入旧版不支持的 `mlas.disable_kleidiai` 配置；1.24.4 不消费该键，配置能回读不代表内核已关闭。

## 聚焦验证结果

所有模型实验均在旧 GUI、游戏、采集和手柄进程退出后逐个运行，不并行占用设备。内存口径为 `proc_pid_rusage` 的 physical footprint，非 RSS。

| 检查 | ORT 1.24.4 | ORT 1.27.0 |
| --- | --- | --- |
| 纯 CPU det，固定 `1×3×640×640`，预热 4 次后 24 个新内容输入的最大增量 | 约 320.08 MiB | 16 KiB |
| 生产 OCR，1920 长边，同一 20 张动态实拍帧两轮共 40 次，最大采样 footprint | 4.177 GiB | 3.181 GiB |
| 上述 OCR 中位耗时 | 269.4 ms | 286.6 ms |
| 上述 OCR 文字及坐标摘要 | 40 次基线 | 40/40 一致 |

固定尺寸、不断变化内容的检测实验独立于识别宽度、采集和业务 Operation。该增长在新版消失；完整 OCR 中位耗时本次约增加 6.4%，不把短样本耗时当作整局性能结论。新版仍有数 GiB 初始化/分配高水位，本次不声称所有内存占用均消失。

闪光和迷失检测各使用 6 张既有代表截图，复用生产预处理、后处理、CoreML 参数及串行调度。两版本的原始输出最大绝对差均为 0，分类/目标框/置信度均一致。profiler 确认闪光实际执行两个 CoreML 分区、CPU 仅原有 Flatten；迷失检测实际执行 CoreML 分区。闪光样本均为 none，不能扩展成红/黄光正样本验收；也不把离线兼容检查当成整局持续实机通过。

正式 `.venv` 更新后，单个原生内存回归测试通过。回归位于独立测试仓 `test/tools/macos/test_ocr_native_memory.py`，默认跳过，仅在设备空闲且显式设置 `ZZZ_OD_TEST_NATIVE_MEMORY=1` 时执行；新进程内 28 次固定尺寸变化内容检测，2 GiB 自身采样上限、60 秒超时，不依赖 `.debug` 截图、不启动上下文或游戏。不得与 GUI/CLI 验证同时运行。

四个模型和四份关键配置的哈希前后一致。完整证据在本机忽略目录 `.debug/macos/memory_astra_20261030/`，包含二进制符号、wheel 元数据/校验、逐阶段 footprint、OCR 摘要与耗时、CoreML 原始输出/profiler、包清单和保护哈希；该目录不作为其他 checkout 的正式能力。
