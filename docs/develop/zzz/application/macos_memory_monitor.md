# Mac 运行内存监测

Mac 的原 GUI、CLI 和调用 `ZContext.init()` 的诊断入口使用同一个监测器。每个进程在 OCR 初始化前记录基线，每十五秒采样，退出时写末态；路径为 `.log/memory/日期_时间_PID.jsonl`，原日志会提示完整文件名。预览、列任务及 Windows 不启动监测。

监测只通过公开 `proc_pid_rusage` / `proc_pidinfo` 查询自身与已经绑定的游戏 PID，不获取 task port、不挂起进程、不抓截图、不枚举窗口、不触发模型加载或推理。使用独立守护线程，不占用 Cocoa 主线程或模型 executor；不在内存保留采样历史，失败只记警告，不阻断自动任务。

每行包含以下内容，字节字段统一使用 bytes：

- 自身及游戏的 RSS、physical footprint、该进程生命周期 footprint 峰值和 pageins；自身原生线程数。
- 当前账户、应用与顶层节点；采集序号和原始像素尺寸。
- 截图历史、迷失检测历史、闪光历史的数量及数组字节数（同一列表内相同数组引用只计一次）；自动战斗策略缓存数量。
- 四个现有 ONNX 会话的对象身份；已有识别/状态线程池的待处理队列长度。这些计数用于发现重复初始化、历史积累或队列积压，不改变队列或识别调度。
- 运行事件总线和原上下文事件总线的监听数量，用于发现已经结束的Operation仍被回调持有。

RSS 是仍驻留在物理内存中的页面，不能覆盖已经压缩或换出的内存。`footprint_bytes` 是 macOS 对进程的内存账本，包含压缩/换出部分的原始计费；因此可以大于实际 RAM，不能解释为该进程此刻占了同量未压缩 RAM。系统压缩池及 swap 用量属于全机指标，应另用活动监视器或系统计数核对，不能与进程 footprint 直接相加。共享页、图形驱动和进程外 Core ML 服务也不能仅凭 RSS 精确分摊。口径参考 [Apple 内存说明](https://developer.apple.com/videos/play/wwdc2022/10106/)。

## 2026-10-30 当前只读证据

Mac mini 本机 16GiB、Apple M6、ORT 1.24.4；7活性/第一队原策略，OCR 使用 CPU，迷失检测和闪光使用 Core ML。无 GUI 的诊断入口 PID46521 于12:23开始，本线程采样：12:38 footprint 11.32GiB、12:39 12.86GiB、12:40 14.89GiB、12:43 17.17GiB；RSS约0.51–0.76GiB，游戏 footprint 约2.3GiB且相对稳定。用户因内存压力要求立即停止并完整重开，不能将这段运行称为稳定的8GB模型开销或完整验收。

12:40 的只读 VM 区域元数据采样中，MALLOC_LARGE 的驻留及压缩/换出页约9.26GiB，MALLOC_SMALL约5.35GiB；IOSurface与IOAccelerator合计约68MiB，线程约86。区域计数不是分配调用栈，不能据此区分 NumPy、OpenCV、ORT、Core ML 或 PyObjC 的具体所有者。日志中 OCR det/rec、迷失检测、闪光会话各只初始化一次；未看到反复加载。原生采集队列深度3、最新帧槽1、普通截图历史最多10张，不能解释持续十几GiB增长。

尚未完成干净进程下的 GUI/CLI同配置对照，因此不能判定是 CLI 特有问题。隔离 Foundation 探针没有复现 `NSRunLoop.runUntilDate_` 自身的大量增长；缺少局部 autorelease pool 目前只是待排查点。证据仅保存在本机 `.debug/macos/memory_analysis_20261030/`，不把忽略文件视为其他部署自带的能力。

优先用此次监测比较完整重开的 GUI：若队列持续增长，先限制同类识别任务的在途数量并淘汰旧帧；若队列和历史稳定而 footprint 增长，再对 OCR 动态尺寸/CPU arena 与 Core ML 分别做相同截图的离线分段对照。原 OCR 实际长边限制由上下文传入1920，覆盖默认960，且 det 预热使用1920正方形、rec批量默认6；这些是 arena 高水位候选，尚无本机纯模块增量。按需评估 arena收缩/复用、较小批量和更聚焦的OCR裁剪，不能直接降低全局识别分辨率后宣称战斗效果不变。

减少10张1080p RGB历史最多约59MiB；采集队列3降2通常只省一个原始BGRA缓冲；降低30fps主要减少复制和CPU开销，会牺牲黄光响应时间，都不应作为十几GiB增长的首要修复。Core ML已按模型哈希保存磁盘编译缓存，清缓存主要影响磁盘和冷启动，并不释放仍存活会话的内存。会话已经复用，任务结束后释放可降低空闲占用，但反复创建会产生延迟与峰值；改CPU、缩小/量化模型或减少识别需要另测本机收益与战斗一致性，不自动更改7活性、队伍及策略。

## 已复现的Operation事件监听泄漏

Operation执行前将暂停和恢复回调注册到`ctx.run_context.event_bus`，结束时此前只从原上下文总线解绑，导致运行总线长期持有结束的指令及其截图。该公共生命周期同时用于GUI和CLI。

离线最小复现中，八个正常结束、各保留一张1080p RGB截图的指令，在GC后仍全部存活，运行总线残留十六个回调，截图合计49,766,400字节；显式从正确总线解绑后全部回收。修复后同一复现没有残留对象、截图或回调。成功、节点失败和初始化异常三种退出路径的最小测试通过，并确认不清除其他订阅者；Ruff通过。代码同时保留原业务总线的清理。

此前GUI PID54073的自动日志记录峰值约7.00GiB，退出时约2.48GiB；其挑战于13:01因非战斗节点超时结束，未完成与CLI相同阶段的整局对照。因此该泄漏已确证，但尚不能认定它解释全部17GiB增长；修复后的实机同负载内存和完整流程继续待验。复现证据在本机诊断目录的`repro_operation_retention_before_fix.json`及`repro_operation_retention.json`。
